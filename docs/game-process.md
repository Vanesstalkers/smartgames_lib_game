# Процесс игры: архитектурные механизмы

## 1. Точки входа и инвариант сессии

- `game.api.new` создает экземпляр игры, сохраняет его в store и регистрирует в Redis-кэше активных игр.
- `game.api.join` связывает пользователя/сессии с игрой через `game.playerJoin` или `game.viewerJoin`.
- `game.api.enter` разрешает вход только при `gameId === user.gameId` и подписывает участника на каналы игры.

Критический инвариант: `user.joinGame()` должен быть выполнен до `enter`, иначе состояние участия считается неконсистентным.

## 2. Создание игры и резолв доменной логики

- Базовый `Game.create()` заполняет состояние через `run('fillGameData')`.
- `run(action)` резолвит обработчик в порядке:
  - `domain.game.actions[gameType]?.[action]`
  - `domain.game[gameType]?.actions?.[action]`
  - `domain.game.actions[action]`
  - `lib.game.actions[action]`
- Такой порядок дает домену приоритет над общими реализациями и формирует расширяемую архитектуру gameType.

## 3. Машина состояний и lifecycle

- Типовой статусный путь: `WAIT_FOR_PLAYERS` -> `IN_PROCESS` -> `FINISHED`.
- Ожидание игроков реализовано через событие `initPlayerWaitEvents` (обработчики `PLAYER_JOIN`/`TRIGGER`).
- `startGame` переводит игру в `IN_PROCESS`, инициализирует process-events и запускает первый `roundStart`.

## 4. Раундовый цикл

- `roundStart`:
  - выбирает доменный/базовый `roundSteps`;
  - обновляет `round`/`statusLabel`;
  - делает `dumpState()` для точки восстановления [Механизм восстановления](game-restoration.md);
  - перезапускает таймер.
- `roundEnd` деактивирует текущего игрока, дергает `END_ROUND`, затем запускает следующий `roundStart`.
- Цикл продолжается до `endGame`.

## 5. Обработка действий клиента

- Клиент отправляет действия через `game.api.action` в форме `{ name, data }`.
- `Game.handleAction()`:
  - определяет контекст игрока;
  - проверяет валидность действия (статус, активность, блокировки);
  - выполняет метод игры или `run(name, ...)`;
  - фиксирует изменения через `saveChanges()`.
- Ошибки маршрутизируются либо в controlled-endgame (`endGameException`), либо в broadcast ошибки в клиентские сессии.

## 6. Событийная шина игры

- Игровые события (GameEvent) регистрируются с наборами handlers (`PLAYER_JOIN`, `TRIGGER`, `END_ROUND`, `PLAYER_TIMER_END` и др.).
- `toggleEventHandlers(handler, ...)` исполняет все слушатели данного handler с проверкой доступа.
- Механизм событий отделяет orchestration (когда исполнять) от доменной логики (что делать).

## 7. Персистентность и broadcast

- Изменения накапливаются в буфере store (`set`/`unset`) и коммитятся через `saveChanges()`.
- Очередь сохранения формирует MongoDB-обновления и после успешной записи публикует изменения в канал `game-{gameId}`.
- Архитектурная цепочка консистентности:
  - `action -> handleAction/run -> set(...) -> saveChanges -> MongoDB -> broadcast`.

## 8. Завершение игры

- `endGame` останавливает таймер, ставит `FINISHED`, исполняет завершающие обработчики и публикует итоговый статус участникам.
- После завершения игра удаляется из активного runtime/кэша через стандартный путь `removeGame`.
