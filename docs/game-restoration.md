# Механизм восстановления: архитектурные механизмы

## 1. Источник истины для восстановления

- В `roundStart` выполняется `dumpState()`.
- Store сохраняет снимок в `game_dump` с привязкой к `_gameid`, `round`, `roundStep`, `_dumptime`.
- `game_dump` используется как recoverable state для:
  - поднятия игры после падения/рестарта воркера;
  - принудительного отката на выбранную точку.

## 2. Базовый механизм `loadGame`

- `loadGame` создает runtime-экземпляр и загружает состояние через `load({ fromDB: { fromDump: true } })`.
- `loadFromDB` выбирает релевантный dump (обычно последний или по query), переносит его состояние в основную коллекцию `game`, затем инициализирует объект в памяти.
- После загрузки вызывается `processData` (доменный пост-процессинг состояния).

Это разделяет восстановление на 2 этапа: storage-rehydrate и domain-reinit.

## 3. Режим восстановления (`restorationMode`)

- После `loadGame` игра помечается `restorationMode` и регистрируется в Redis как восстановленная.
- Затем запускается `initPlayerWaitEvents` для повторного входа участников.
- Инвариант: продолжение партии выполняется через `restart()` из восстановленного снимка, а не через `startGame` новой партии.

## 4. Восстановление после рестарта воркера

- Лобби определяет необходимость восстановления, если у пользователя есть `gameId`, а активной игры нет в кэше/канале.
- Клиент вызывает `game.api.restore`.
- Варианты:
  - если игра не поднята (`needLoadGame`), выполняется `loadGame` + повторный join;
  - если уже поднята другим запросом, выполняется только повторное присоединение.

Главный архитектурный эффект: несколько клиентов могут безопасно "сойтись" в один восстановленный runtime.

## 5. Принудительный откат (`restoreForced`)

- По `round`/`roundStep` выбирается dump.
- Текущий runtime игры удаляется через `removeGame({ preventDeleteDumps: true })`.
- Из выбранного dump поднимается новая runtime-версия (`loadGame` с query).
- Участники с активным состоянием повторно подключаются к восстановленной игре.

Это атомарный swap runtime-состояния: старый инстанс удаляется, новый создается из snapshot.

## 6. Ключевые архитектурные инварианты

- `game_dump` — единственный источник восстановления состояния раунда.
- `restorationMode` обязателен для корректного перехода в "продолжение", а не "новый старт".
- `removeGame(...preventDeleteDumps)` обязателен для отката без потери истории снимков.
- Повторный join участников после восстановления — необходимая часть консистентности session/game связей.
